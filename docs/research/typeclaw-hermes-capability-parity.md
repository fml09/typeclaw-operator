# TypeClaw–Hermes capability parity baseline

Status: research baseline for issue #2  
Observed: 2026-08-18

## Conclusion

TypeClaw Operator should reuse Hermes Operator's Kubernetes control-plane patterns, not port Hermes' API or runtime model. TypeClaw already supplies the foreground agent process, Agent Folder semantics, configuration, channels, graceful termination, and Git-based history; those are **Direct** capabilities. Kubernetes reconciliation, persistent storage, exposure, backup jobs, audited SelfConfig, auto-update, status, conformance, and release packaging are **Adapt** work because their resource shapes must follow TypeClaw's concepts and invariants. A complete managed-runtime image, managed secret write-back/restart capabilities, a Kubernetes-compatible sandbox contract, and meaningful health/metrics surfaces require **Upstream** TypeClaw work or an upstream-approved contract. Hermes-only Honcho support, its literal OpenClaw importer, and multi-active/HPA behavior are **Exclude** items for the initial parity baseline.

This classification is a planning boundary, not an implementation decision. In particular, it does not decide the API field set, storage/secret boundary, pod-security envelope, rollout mechanics, or exposure defaults. The approved Wayfinding Map already fixes the distribution set—OCI Helm, plain manifests/Kustomize, OLM, signed multi-architecture images, and SBOM attestations—and support for the latest three upstream-maintained Kubernetes minors. The remaining release decision is how to name, publish, version, upgrade, and prove those artifacts and compatibility promises.

- Only upstream primary sources at those revisions are used. When prose and executable artifacts disagree, source, tests, generated release metadata, and release workflows take precedence. “Direct” means the TypeClaw behavior is authoritative and can be preserved without a new upstream contract; it does not mean zero operator code. “Adapt” means the capability belongs in this product but Hermes' schema or mechanism cannot be copied literally. “Upstream” means a missing TypeClaw runtime contract blocks a production-quality mapping. “Exclude” means there is no TypeClaw parity obligation at this baseline.

## Runtime and image

The foreground runtime is already suitable in shape: `/agent` is the Agent Folder, `typeclaw run` owns the session and WebSocket/channel runtime, and the process performs awaited shutdown. The missing contract is packaging. TypeClaw publishes a versioned multi-arch **base** image before npm publication, but the generated final image deliberately omits the Agent Folder and dependency installation because `typeclaw start` bind-mounts them ([release workflow](https://github.com/typeclaw/typeclaw/blob/ae16f5b525171f335989e86606247673937a4bcd/.github/workflows/release.yml#L232-L334), [Dockerfile generator](https://github.com/typeclaw/typeclaw/blob/ae16f5b525171f335989e86606247673937a4bcd/src/init/dockerfile.ts#L1368-L1435)). Hermes' self-contained upstream image is therefore an architectural example, not a drop-in artifact ([Hermes StatefulSet](https://github.com/paperclipinc/hermes-operator/blob/4c726aed16502e8dc23980c04b3780cb69a92e08/internal/resources/statefulset.go#L61-L115), [image/state split](https://github.com/paperclipinc/hermes-operator/blob/4c726aed16502e8dc23980c04b3780cb69a92e08/internal/resources/statefulset.go#L322-L329)). A prototype must prove a pinned TypeClaw image can hydrate or mount dependencies, start without Docker/hostd, preserve the Agent Folder, and upgrade deterministically.

## Resource and API surface

The resource model should expose TypeClaw concepts—TypeClaw Instance, Agent Folder, Managed Runtime, config/channels, lifecycle, storage, security, exposure, backup, and SelfConfig—not transliterated Hermes fields. Hermes validates that one primary instance resource plus a separate audited request resource and cluster-wide unset-value defaults can work. Its implementation also shows why the TypeClaw API must choose pointer/value shapes deliberately: empty strings and zero numeric values are overwritten just like `nil`, while pointer booleans can preserve explicit false. Hermes does not establish which fields TypeClaw should expose. Raw pod escape hatches also need an explicit product-policy decision; their presence in Hermes is evidence of extensibility, not an automatic requirement.

## Lifecycle and availability

A single-active StatefulSet with retained storage is the conservative adaptation because TypeClaw owns a session and mutates one Agent Folder. Suspend-to-zero and rolling replacement are plausible control-plane behaviors, but readiness gates, termination grace, update ordering, and what happens to live channel sessions require prototype evidence. HPA/multi-active behavior is outside this baseline until TypeClaw documents shared-state and message-delivery correctness. A PDB can still be considered for voluntary disruption protection, independently of HPA.

Hermes' opt-in auto-update is part of the full-parity baseline, but its implementation is not directly portable. The lifecycle decision must define confirmation and rollback semantics; the persistence decision must define whether a successful pre-update backup is mandatory; and the release decision must define channels, desired-vs-running version ownership, promotion into Git, and compatibility constraints. All of those depend on the upstream Managed Runtime image and readiness contracts.

## Agent Folder state and secrets

The Agent Folder is not an opaque PVC. TypeClaw distinguishes human-managed config, system-managed state, ignored credentials/workspace, and selected force-committed history. Consequently, Git history, volume durability, backup snapshots, and Kubernetes Secrets solve different problems and must not be presented as interchangeable. In particular, `.env` and `secrets.json` are truly ignored while sessions and other runtime paths may be force-added ([gitignore policy](https://github.com/typeclaw/typeclaw/blob/ae16f5b525171f335989e86606247673937a4bcd/src/init/gitignore.ts#L7-L56)).

The unresolved boundary is mutable secret state. Environment/Secret projection covers initial injection, but OAuth refresh and adapter write-back require writable persistence; KakaoTalk also relies on a key outside the Agent Folder. The operator must not silently put all of that in the Agent Folder PVC or Git. The storage layout and API/provider contract are human and upstream decisions, respectively.

## Backup, restore, and migration

Native Git backup remains a Direct TypeClaw feature, but it is not a disaster-recovery snapshot because ignored paths are intentionally absent. A separate S3-compatible snapshot facility can adapt Hermes' scheduled, pre-update, on-delete, retention, empty-destination restore, and bounded-finalizer patterns. The TypeClaw version must define an allowlist or exclusion contract for credentials and ephemeral caches, record format/version metadata, and restore into a quiesced single-active instance.

Hermes' checked-in backup implementation is not a production oracle: its full E2E is unconditionally skipped, while the Job script assembles several tool and writable-filesystem assumptions that the test does not exercise ([backup Job](https://github.com/paperclipinc/hermes-operator/blob/4c726aed16502e8dc23980c04b3780cb69a92e08/internal/resources/backup_job.go#L46-L111), [skipped E2E](https://github.com/paperclipinc/hermes-operator/blob/4c726aed16502e8dc23980c04b3780cb69a92e08/test/e2e/backup_restore_test.go#L12-L24)). Reuse the lifecycle pattern only after TypeClaw-native executable tests pass.

“Migration” should initially mean importing or restoring a validated existing Agent Folder. Hermes' literal OpenClaw CR/PVC discovery and `hermes-agent migrate from-openclaw` invocation are not parity. Copy/move semantics, destructive-source handling, and supported old Agent Folder versions remain human decisions.

## Security

The current TypeClaw sandbox assumes a single-tenant Docker trust boundary and explicitly disables seccomp so `bwrap` can create namespaces; optional network and `realProc` modes add capabilities. Hermes instead demonstrates `RuntimeDefault` seccomp and disabled privilege escalation for its different s6 runtime ([Hermes security context](https://github.com/paperclipinc/hermes-operator/blob/4c726aed16502e8dc23980c04b3780cb69a92e08/internal/resources/statefulset.go#L29-L59)). Neither proves that TypeClaw works under the intended cluster admission policy. The project needs a prototype of `bwrap`, UID/GID/PVC ownership, writable root paths, network filtering, and subagent isolation before promising a security profile. Any weaker admission posture must be a visible user choice, not an implicit fallback.

## Networking, channels, and exposure

TypeClaw's fixed internal port `8973`, WebSocket paths, token checks, and channel adapters are Direct runtime facts ([port](https://github.com/typeclaw/typeclaw/blob/ae16f5b525171f335989e86606247673937a4bcd/src/container/port.ts#L7-L16), [server](https://github.com/typeclaw/typeclaw/blob/ae16f5b525171f335989e86606247673937a4bcd/src/server/index.ts#L434-L484), [channels](https://github.com/typeclaw/typeclaw/blob/ae16f5b525171f335989e86606247673937a4bcd/README.md#L27-L30)). Kubernetes Service, NetworkPolicy, Ingress, Gateway API, and Tailscale are Adapt mechanisms. Defaults cannot be copied from Hermes: TypeClaw channels and model/tool traffic have different and partly dynamic egress needs, while TypeClaw's own `network.blockInternal` installs in-container iptables rules. The prototype must establish whether platform NetworkPolicy replaces, complements, or conflicts with that layer. Hostd portbroker and container-side tunnel behavior should be replaced by platform resources rather than carried into the Managed Runtime.

## SelfConfig and GitOps

TypeClaw already permits selected agent edits and blocks privilege-promoting config changes. A Kubernetes SelfConfig resource can add audit, policy, status, idempotency, and SSA field ownership, but it must request TypeClaw-native operations rather than expose Hermes' action list verbatim. The runtime-to-operator submission mechanism, restart-required changes, credential writes, protected paths, conflict behavior, and Git reconciliation are unresolved contracts. Hermes' documentation also overstates conformance here: its own workflow marks the real GitOps coexistence suite as a placeholder, so the operator needs its own proof.

## Observability and status

Kubernetes conditions, events, observed generation, replica state, backup/restore state, and bounded-cardinality controller metrics are Adapt work. Condition names should describe TypeClaw-owned milestones—runtime image ready, Agent Folder mounted, configuration accepted, secrets available, runtime ready, backup/restore outcomes—rather than mirror Hermes' catalogue. Hermes' pinned aggregate `Ready` calculation is based on StatefulSet replica readiness, not proof of every documented subsystem condition ([controller](https://github.com/paperclipinc/hermes-operator/blob/4c726aed16502e8dc23980c04b3780cb69a92e08/internal/controller/hermesinstance_controller.go#L721-L750)). The generic TypeClaw HTTP 200 can support an early process probe, but it does not distinguish alive, initialized, channel-ready, or degraded states; a production readiness/metrics contract belongs upstream or must remain explicitly operator-local and narrow.

## Testing and conformance

TypeClaw's package defines typecheck, lint, format, and parallel unit-test gates ([package scripts](https://github.com/typeclaw/typeclaw/blob/ae16f5b525171f335989e86606247673937a4bcd/package.json#L33-L43)). The operator needs additional envtest and real-cluster coverage for reconciliation idempotency, admission denials, SSA conflicts, single-active rollout, suspend/resume, backup/restore, secret rotation, NetworkPolicy, upgrade/skew, and both supported architectures. Hermes is useful for test categories, but its placeholders and single-version E2E job must not be cited as proof of a complete conformance matrix.

## Distribution and release

Hermes provides an adaptable release pipeline for multi-arch images, digest signing, SPDX SBOM generation/attestation, Helm OCI, binaries, and a plain installer. Its `0.1.20` bundle was accepted into the immutable [community-operators](https://github.com/k8s-operatorhub/community-operators/tree/0b2425327054b7204dec05549f794043501db899/operators/hermes-operator/0.1.20) and [community-operators-prod](https://github.com/redhat-openshift-ecosystem/community-operators-prod/tree/2c33b45e8ee793fd12df5e4f7971ac9c9f57b06e/operators/hermes-operator/0.1.20) catalog histories, despite stale checked-in CSV fields. TypeClaw Operator must establish its own published locations, provenance, install and upgrade tests, and the executable test matrix for the approved latest-three Kubernetes support window. TypeClaw's release verifies a multi-arch base image and npm provenance, but the pinned workflow has no container-signing or image-SBOM stage ([TypeClaw release workflow](https://github.com/typeclaw/typeclaw/blob/ae16f5b525171f335989e86606247673937a4bcd/.github/workflows/release.yml#L232-L420)). The Managed Runtime image is a separate upstream supply-chain dependency from the operator image; signing the operator does not solve the missing complete TypeClaw runtime artifact.

## Upstream contribution implications

The smallest upstream agenda implied by this baseline is:

1. Define and publish a complete, pinned Managed Runtime image contract, including dependency hydration, entrypoint, writable paths, UID/GID behavior, and upgrade compatibility.
2. Make the managed deployment profile executable and provide runtime contracts for writable secret state and self-restart/request signaling. TypeClaw already identifies these seams and the remaining Docker escape hatches; this work should land behind those upstream interfaces rather than in an operator-only fork.
3. Establish a Kubernetes-compatible sandbox/security mode and document which capabilities, seccomp features, filesystems, and namespaces are required.
4. Add health semantics—and metrics only if TypeClaw wants to own runtime metrics—that distinguish process availability from initialized/ready/degraded state.

These are contribution candidates, not commitments. A prototype may show that a narrower operator-local adapter is sufficient for one or more items, but that result should be recorded before reclassifying them.

## Facts still needing prototype or human decision

Prototype evidence is still required for:

- booting the pinned release without Docker/hostd from a reproducible image on amd64 and arm64;
- Agent Folder/PVC permissions, dependency installation, restart, and upgrade with no concurrent writer;
- `bwrap` and TypeClaw network filtering under the intended admission and CNI policies;
- probe timing, graceful termination, channel/webhook cleanup, and reconnect after replacement;
- backup quiescing, secret exclusion, empty-target restore, and version-skewed Agent Folder import;
- SelfConfig submission, SSA conflict handling, and restart-required mutations.

Human decisions remain for:

- CRD granularity, public field set, defaulting precedence, and raw pod escape hatches;
- the Agent Folder/Secret/external-key storage boundary and backup retention policy;
- security baseline and whether any opt-in weaker sandbox mode is acceptable;
- suspend, rollout, deletion/final-backup, and single-active availability semantics;
- default exposure, outbound network policy, Tailscale/Gateway API scope, and channel-specific egress;
- SelfConfig allowlists, protected paths, force-ownership policy, and GitOps authority;
- artifact names and registry locations, operator/runtime/chart version coupling, promotion and deprecation rules, upgrade guarantees, and how the approved latest-three Kubernetes support policy is exercised and proven. OLM publication and the required distribution channels themselves are already fixed by the approved Map.
